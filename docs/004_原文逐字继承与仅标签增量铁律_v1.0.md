# 《无职转生 - 沙盒 · 因果法典》
# 原文逐字继承与仅标签增量铁律 v1.0

> 本文件用于消除“部分人物/时间线不能按原文继承”的错误施工理解。
> 最高原则：**原有条目正文必须继承；本项目只在明确位置做最小增量，不允许以重写、摘要、改写代替原文。**

## 1. 原有97名人物条目

授权母卡原有97名人物条目必须完整继承原文内容与原字段结构。

禁止：
- 因为新增帝皇娘/十二原体娘而重写原有人物；
- 把原人物正文改成摘要；
- 用新模板覆盖旧人物正文；
- 为了“统一格式”而改写原人物；
- 删除原人物条目中的原有细节；
- 以“当前仓库没有单独角色md”为理由自行重建人物正文。

本项目对原人物条目的默认操作是：**0改写**。

新增人物只有：
- 人类帝皇（帝皇娘）1条；
- 十二原体娘12条。

这13条是新增，不是替换任何原人物。

## 2. 原有46条时间线

授权母卡原有46条时间线的剧情原文、事件顺序、原有标签/格式与叙事内容必须完整继承。

本项目对这些时间线所做的工作是**标签增量**，不是剧情重写。

允许插入：
- `RUNTIME_BASELINE` 注释；
- 已封板的 `[因果:...]` 机器标签；
- 已封板的 `[纠正:CORR-*]` 机器标签；
- 为运行时去重所需的机器ID；
- 不改变原文事实的极少量机器注释。

禁止：
- 删除原时间线句子；
- 改写原事件描述；
- 把原时间线摘要化；
- 把多个原事件合并成一条；
- 因为机器标签存在而重写事件正文；
- 用本项目working文档中的说明文字替换母卡原时间线正文。

正确形式应当是：

`原时间线正文 + 最小机器标签/注释`

而不是：

`根据原时间线重新写一份新版剧情`

## 3. 原文来源优先级

原文唯一事实源是授权母卡 v5.3.0 的只读 JSON/PNG 中的 `character_book`。

若 GitHub 仓库没有把某个原人物/原时间线单独展开成 md 文件，**不代表原文不存在，也不代表不能继承**。

静静必须从授权母卡只读副本中复制完整 `character_book` 到派生工作副本，再对指定条目做最小 patch。

禁止仅依据 GitHub 的零件文档反向重建母卡正文。

## 4. patch 施工模型

正确施工：

`授权母卡 character_book 全量复制到派生副本`
→ `保持原entry正文与元数据`
→ `对46条时间线定位指定事件`
→ `仅插入已封板机器标签/RUNTIME_BASELINE`
→ `新增帝皇Overlay/运行时规则/帝皇娘/十二原体娘/MVU条目`
→ `生成Candidate`

原条目不是“重新生成对象”，而是“继承对象后做局部 patch”。

## 5. 允许变化的原条目范围

除46条时间线的机器标签增量，以及已明确设计的兼容槽位复用外，原有条目正文默认不变。

尤其：
- 原97人物正文：逐字继承；
- 原30地点正文：逐字继承；
- 原41核心设定正文：逐字继承；
- 原status/combat/output/memory等成熟条目：逐字继承；
- 原46时间线：原文逐字继承，只插机器标签/注释。

如果某项业务确实要求修改原文，必须有单独、明确、已批准的施工单；当前不存在这种授权。

## 6. 无法读取原文时的处理

若静静发现某个原条目无法从授权母卡读取、解析失败或字段损坏：

必须：
1. 停止该条目施工；
2. 报告具体entry名称/ID/读取错误；
3. 保留其他可正常继承条目；
4. 等待修复读取链路。

绝对禁止：
- 自行补写；
- 根据记忆重构；
- 从wiki替代；
- 用summary占位；
- 声称“不能继承所以改写”。

## 7. QA硬门槛

Candidate1 必须做原文继承QA：

### 人物
- 原97名人物条目数不减少；
- 对原人物正文做规范化前后文本比对，应为0业务改写；
- 新增13人必须与原97人分离。

### 时间线
- 46/46原时间线仍存在；
- 去除本项目新增机器标签/注释后，与授权母卡对应原时间线正文一致；
- 原事件顺序一致；
- 不得出现摘要替换或段落丢失。

### 其他原条目
- 地点/核心设定/status/combat/output/memory不得出现无授权正文改写。

若任何原条目无法通过继承比对，Candidate1 不得标记PASS。

## 8. 一句话铁律

**原文全部继承；时间线只打标签；新增内容只新增；读不到就停，绝不自己重写。**
